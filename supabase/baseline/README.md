# Rebuilding the STRYT database (baseline + migrations)

**Decision D7 (a):** the database is rebuildable from an official **schema baseline** taken from production, plus every migration whose ledger version is **greater than the baseline cutoff**. Migrations older than the cutoff are history: 48 of the 90 app tables were created in the dashboard and exist in no migration, so replaying `supabase/migrations/` from the start cannot rebuild production.

## Files

| File | What |
|---|---|
| `2026-09-15_schema.sql` | Every app object in `public` and `private`, in restorable order: extensions, schema, enums, tables (with defaults), functions, constraints (keys/checks first, then foreign keys), indexes, triggers (including `auth.users → handle_new_auth_user`), row level security, policies, exact table/column/function grants. |
| `2026-09-15_platform_state.sql` | Storage buckets and `storage.objects` policies, the `supabase_realtime` table list, cron jobs, and a migration ledger with one baseline row at the cutoff. |

**Cutoff:** ledger version `20260915163940` (`20260972_provider_leads_rpc_and_lead_sender_check`). The header of each file repeats it.

Both files were generated by `scripts/baseline/dump-baseline.mjs` from `pg_catalog` through the Management API (read-only; no Docker, no `pg_dump`, no database password). Every statement comes from catalog functions (`pg_get_functiondef`, `pg_get_constraintdef`, `pg_get_indexdef`, `pg_get_triggerdef`, `pg_policies`, ACLs), not retyped. Items are separated by `-- @@item` lines.

## Rebuild procedure (staging or a throwaway project — never production)

1. **Target check.** The applier refuses production (`gnswxlfmcwyhmzlfipql`) and any ref other than D6's staging ref.
2. Apply the schema: `node scripts/baseline/apply-baseline.mjs <staging ref> supabase/baseline/2026-09-15_schema.sql`
3. Apply platform state: `node scripts/baseline/apply-baseline.mjs <staging ref> supabase/baseline/2026-09-15_platform_state.sql`
4. Apply every migration file applied to production **after** the cutoff, in ledger order (see `supabase/APPLY_LOG.md`), and add its ledger row.
5. Seed synthetic data (staging only): `npm run seed:staging -- --reset`.
6. Prove it: `SNAPSHOT_PROJECT_REF=<staging ref> node scripts/snapshot-live-schema.mjs <scratch>/staging.sql`, a fresh production snapshot, and `diff` (skip the 9 header lines).

The applier sends items in batches of 40; each batch is one transaction (tested), and on failure it re-runs the batch item by item to name the failing item. Resume with `--from N`.

## Verified on 2026-09-15 (staging `laswruzdyqehziyupmdm`)

- Schema: 1,566 items applied with 0 errors; platform state: 46 items.
- Staging snapshot vs production snapshot: identical except
  - `pg_net` 0.20.4 on staging vs 0.20.3 (extension patch version available per project);
  - two policies (`agreements.read_agreements`, `custom_payments` read) whose text lost redundant parentheses when re-parsed (`(A OR B) OR C` → `A OR B OR C`) — same meaning;
  - migration ledger: 159 rows vs 1 baseline row.
- Not in the snapshot, compared separately: 7,211 column SELECT grants, 248 function EXECUTE lists, 3 storage buckets, 3 cron jobs, 34 realtime tables, RLS flags on 91 tables — all identical.

## Not in the baseline (by design)

| Missing | Why / what to do |
|---|---|
| Row data | Staging must never hold production personal data. Seed synthetic data. Categories (reference data) are copied by the seed script. |
| Vault secrets (`functions_url`, `service_role_key`) | Values are secrets. Set staging's own values in the dashboard if a staging trigger needs them (push delivery through `pg_net`). |
| Event trigger `ensure_rls` → `rls_auto_enable` | Creating event triggers needs superuser; the Management API role isn't one. Staging doesn't auto-enable RLS on *new* tables — every migration must enable RLS itself (the migration linter checks policies; add RLS explicitly). |
| Auth, storage and realtime internals | Owned by Supabase per project. |
| Edge functions and their secrets | Deployed separately: `npx supabase functions deploy <name> --project-ref <ref> --use-api`. |

## Regenerating

`node scripts/baseline/dump-baseline.mjs <YYYY-MM-DD>` writes new files with the current cutoff. Regenerate after a large batch of migrations so the rebuild replays less; keep the old files until the new ones are proven on staging.
